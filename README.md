# OfferLens · 评测与回归平台（工程骨架）

求职诊断 Agent（内层被测对象）+ 评测回归平台（外层）。

一份简历 × 一份 JD 进去，Agent 产出改进建议；平台负责回答一个问题：

> **换模型 / 换 prompt 之后，建议到底是"真的变好了"，还是只是看起来变好了？**

这个仓库是那套平台的**工程骨架**：数据怎么造、指标怎么算、差异怎么判显著、结果怎么落库、报告怎么出。
`npm run demo` 五秒出全流程结果，**不花一分钱**，离线可跑；
真实模型那一侧也已经**真跑过一轮**（144 次运行 + 48 组裁判，实花 ¥6.26），结论在「第四·补」节。

> 那一轮最有价值的部分不是"涨了多少"，而是**它把三个只会在真数据上暴露的问题照了出来**：
> 裁判其实在给自己打分、核心指标的"源"漏了一整份输入文档、裁判崩一次就把钱全打水漂。
> 详见「第四·补」的问题清单 —— 那些是设计阶段想不到的。

```bash
npm install
npm run db:init      # 建库（9 张表）
npm run cases:build  # 生成 24 组评测集
npm run demo         # 端到端跑通：数据 → 指标 → 对比 → 落库 → 报告
npm test             # 100 个单测
npm run typecheck
```

## 一、这个项目最容易被问倒的地方，以及它的答案

**"简历诊断没有标准答案，你怎么知道建议是对的？"**

这是整个项目的地基。如果答不上来，前面所有数字都会被当成自嗨。
所以仓库里所有的指标都是**代理指标（proxy metric）**，且每一个都写清了三件事：定义、怎么抽、已知误报来源。

| 指标 | 它实际在测什么 | 已知误报来源 / 怎么校准 |
| --- | --- | --- |
| **无源实体率** | 建议里出现的实体（技术名词/数字/项目名），有多少在简历原文里找不到出处 | 词典外的新技术会被误判；已用「白名单 + 归一化 + 豁免规则」压制，并要求报 P/R/F1 而不是一个裸百分比 |
| **硬门槛覆盖率** | JD 的硬性要求里，建议覆盖了几条 | 靠关键词归一命中会虚高 → 必须带**段 ID 锚点**才算数，抄 JD 原文拿不到分 |
| **建议可执行性（1–3）** | 这条建议"能不能照着做" | LLM-as-judge 会自证，所以 judge 与生成器**必须换模型**，并用人工标注校准一致率（Cohen's κ） |
| **pass^k** | 同一配置重复跑 k 次，**每次都过**的 case 比例 | 只看单次成功率会掩盖"时好时坏"，pass^k 就是用来暴露这一档的 |
| **步骤级指标** | 步数、token、耗时、重试、死循环 | 非确定轨迹不能按 step 序号做跨版本 diff（见下） |

> 唯一的地面真值来源是**人工标注**（24 组 golden + 40 条建议抽检），其余全部是代理指标。
> 这不是妥协，这是这个场景的客观形态——把它明说出来比假装有真值要可信。

## 三、四块交付件分别解决了什么

### ① trace / schema 与 SQLite 建库

- `StepSpan`：`span_id / parent_id / trace_id / type(llm|tool|agent) / name / start / end / tokens / retry_of / error / attrs`
- `schema.sql` 9 张表，关键是 **`result` 的主键是 `(run_id, case_id, run_index)`** ——
  所以重跑 demo 不会重复计费，这是幂等性的落点。
- 用 Node 内置 `node:sqlite`，**不装任何原生依赖**（better-sqlite3 在 Windows 上编译是常见翻车点）。

### ② 24 组 case 组装（固定种子分层抽样）

- 4 份简历 × 6 个 JD = 24 组，**固定种子 `20261004`**，每次跑结果完全一致。
- 分层约束：每份简历至少出现一次、4 类岗位全覆盖、4 组 golden、4 组 hard negative。
- `hard-negative` 的判定写在 `build-cases.ts` 里：高级岗 × 经历单薄、非相关专业 × 明确要求、转行简历 × 平台岗（技术栈错配）。

### ③ 指标与统计纯函数

全是纯函数 + 单测，不依赖任何外部服务：

- `mcnemar(b, c)`：连续性校正版 χ² 与精确二项检验，返回 `{ statistic, p, significant }`
- `pairedBootstrapCI(a, b, { seed, iters })`：**成对重采样**（不是各取各的），固定种子可复现
- `cohensKappa(matrix)`：judge 与人工标注的一致率
- `passK(outcomes, k)`：**按 `(run_id, case_id)` 分组**——不按配置分组的 pass^k 是错的
- `sliceDown(...)` + `partitionFindings(...)`：切片下钻，能力类差异全保留、成本/延迟类折叠

### ④ 端到端 demo（不花钱验证整条管线）

用合成数据把链子跑通，四段输出：指标口径 / payload 稳定性 / 对比矩阵 / 落库。

## 四·补、真实模型实测结果（2026-10-04 · DeepSeek）

**这一节是真花钱跑出来的，不是合成数据。**

规模：24 组 case × 2 档位 × 3 次重复 = **144 次 Agent 运行**，加 **48 组裁判**（正反序各一次 = 96 次裁判调用）。
实验设计上两档只差一个变量：`p2-strict` 在 `p1-baseline` 基础上**只加了一条约束** ——
每条建议必须绑定简历段 ID，且不许引入简历里没有的数字与实体。

### 主结果

| 指标 | p1-baseline | p2-strict | 判定 |
| --- | ---: | ---: | --- |
| 达标率 | 0.125 | **0.792** | McNemar p=0.0000，显著更好 |
| 无源实体率（严口径） | 0.259 | **0.105** | 95%CI [-0.195, -0.112]，显著更好 |
| 带锚点覆盖率 | 0.808 | **1.000** | 显著更好 |
| 建议可执行性（1–3） | 3.000 | 2.977 | 显著**更差**（幅度 0.023） |
| 单次成本 | ¥0.048 | ¥0.055 | 不显著 |
| P95 延迟 | 40.1 s | 45.3 s | 显著更差 |

**一句话结论**：加一条"必须给出处"的约束，把编造率砍掉一半（25.9% → 10.5%），
达标率从 12.5% 抬到 79.2%，代价是可执行性评分微降、延迟上升约 12%。
**这是一个有代价的改进，不是免费的午餐** —— 只报"达标率大涨"就是把代价藏起来了。

> ⚠️ **这一节的成本数字已被证伪，请连着下一节一起看。**
> 跑完这批之后发现 `extraBody`（关思考参数）**从未真正送达请求体**，
> 也就是说这 144 次运行的输出里一直混着思维链。
> 修复后同一提示词下每 run 输出 **~6100 → ~950 token**，
> 所以表中"单次成本 ¥0.048 / ¥0.055"**高估了约 6 倍**。
> 质量类指标（达标率、无源实体率、锚点覆盖率）的相对比较仍然成立 ——
> 两档是在同样的错误条件下跑的，但**绝对成本不能引用**。

### 稳定性：pass^k 的真正价值

```
flash__p1-baseline   pass^3 = 0.000（0/24）· 全过 0 / 时好时坏 10 / 全挂 14 · 不稳定率 42%
flash__p2-strict     pass^3 = 0.542（13/24）· 全过 13 / 时好时坏 10 / 全挂 1 · 不稳定率 42%
```

两档的**不稳定率都是 42%**：有近一半 case 的表现是"时好时坏"。
只看单次成功率，你会以为两者只是"好一点"和"差一点"；实际上一个是稳定可用，另一个接近掷硬币。
**这就是 pass^k 存在的全部理由。**

### 切片下钻

14 条显著差异全部同向：p2-strict 在**所有**岗位类别、所有简历画像上都更好，
没有出现"整体变好但某子集退化"。其中 `category=business` 的达标率从 0.000 → 1.000。

> 这里没有"某子集悄悄退化"的戏剧性发现 —— 与其编一个，不如如实说这版 prompt 是全面改善。

### 这次实测暴露并修掉的问题（真实清单）

1. **裁判根本没换模型**。`judgeSuggestions(r.profile.model, …)` 传的是被测模型本身，
   等于让它给自己打分；"跨族裁判"的选择只出现在一行打印里。**自证式评审比没有评审更糟。**
2. **无源实体率的"源"只算了简历**。于是"岗位要求「熟悉 Vue」，简历只有 React" 这种**正确的缺口分析**
   被判成编造 —— 真实数据里 `tech:vue` 出现 252 次、`tech:echarts` 222 次。
   把 JD 原文也计入"源"后，两档均值从 0.568 / 0.441 降到 0.253 / 0.102。
3. **`pearson([], [])` 抛异常**，裁判阶段在第 0 条就崩，已花掉的生成成本差点白搭。
4. **裁判结果没落盘**，崩溃就得重打一遍。现在 `data/real/judge.jsonl` 支持续跑。
5. **断点续跑会丢记录**：跳过时没写回 runs JSONL，汇总只读到本次新写的部分。
6. **`deepseek-flash` 默认开思考模式**，不改会烧钱且 JSON 解析失败（见上）。

### 诚实的局限（必须一起说）

- **裁判是同族**。DeepSeek-V4-Pro 裁 DeepSeek-V4.1-Flash 的输出。报告里打了警告。
  要干净结论，加一个免费的硅基流动 key 就能换成跨族 Qwen3-8B。
- **判分天花板**。p1-baseline 的可执行性被打成满分 3.000 —— 说明裁判在这个维度**没有区分度**，
  "3.000 → 2.977 显著更差"要打问号。这是 judge 的问题，不是 prompt 的问题。
- **没有人工校准**。`data/gold/labels.jsonl` 不存在，所以所有 judge 结论只能算**参考**。
- **V4-Pro 档位没跑**（实测单次 ¥0.377，是 flash 的 7.4 倍）。因此**没有资格回答"换更贵的模型有没有用"**。
- 实际花费 **¥6.26**（余额 ¥9.93 → ¥3.67）。报告里的成本按**峰时价**记账，是刻意高估，谷时只花一半。

## 四·补二、跨厂商实测（2026-10-04 · 硅基流动中国站）

DeepSeek 那次只回答了"prompt 改一下有用吗"。这一批换平台、换问题：
**同一件事，让不同厂商的模型做，谁做得好、值不值。**

- 平台：硅基流动**中国站**（`api.siliconflow.cn`）　额度：¥16　实花 **¥2.28**
- 矩阵：4 档位 × 24 组 case × 3 次重复 = 288 次运行，全部只跑 `p2-strict`
  （p2 已证明显著优于 p1，换模型时把它固定住，才分得清差异来自哪边）
- 裁判：`tencent/Hunyuan-A13B-Instruct` —— 与矩阵里四族**全部不同族**（跨族 ✅）

### 结果

| 档位 | 模型 | **产出率** | 无源实体率 | 锚点覆盖 | 达标率 | pass³ | 单次成本 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `sf-dsv4flash` | DeepSeek-V4-Flash | 1.000 | 0.109 | 1.000 | 0.625 | 0.375 | ¥0.0125 |
| `sf-qwen35-122b` | Qwen3.5-122B-A10B | 1.000 | **0.087** | 0.993 | **0.653** | **0.500** | ¥0.0072 |
| `sf-qwen35-27b` | Qwen3.5-27B | 1.000 | 0.103 | 1.000 | 0.597 | 0.417 | **¥0.0049** |
| `sf-glm45-air` | GLM-4.5-Air | **0.583** | 0.057 | 0.961 | 0.431 | 0.167 | ¥0.0038 |

1. **产出率是前置门槛，必须先看**。GLM-4.5-Air 有 **42%（30/72）的运行根本产不出结构化结果**
   —— 它会在 JSON 字符串里写未转义的中文引号（`将"了解 WebSocket"改为`），JSON 天然非法。
   把它那 30 次混进质量均值，无源实体率会被算成 0.033、全场最低，看起来最干净。
   现在这一类单独成列，并计入达标率分母与 pass^k。
2. **Qwen3.5-122B-A10B 是这批里的最优解**：达标率与 pass³ 都最高，无源实体率显著优于 DeepSeek
   （0.115 → 0.072，95% CI 不含 0），而单次成本只有它的 **58%**。
3. **Qwen3.5-27B 是最便宜的可用档**：¥0.0049/次（DeepSeek 的 39%），无源实体率与它无显著差异，
   且可执行性反而显著更高（2.841 → 2.925）。代价是**慢**：p50 单次 54 秒 vs DeepSeek 的 17 秒。
4. **DeepSeek-V4-Flash 在硅基流动上比原厂便宜约 4 倍**（¥0.0125/次，原厂峰时价 ¥0.051），
   表现与原厂那批同量级 —— 但两边**不能混进同一张表**，转发站的量化与后端都不同。
5. **所有档位都不稳定**：pass³ 最高只有 0.500，不稳定率 29%–54%。
   这批数据不支持"接一个模型上线就完事"，得配回归监控。

### 这次发现并修掉的 bug（比结果本身更值钱）

**`extraBody` 从来没生效过 —— "关思考"是假的。**
`catalog.ts` 声明了 `extraBody`，`llm.ts` 也写了 `Object.assign(body, extraBody)`，
但 `offerAgent.ts` 与 `llmJudge.ts` 构造 `LlmClient` 时**都没把它传进去**。
声明端和消费端都在，中间断链，静态看完全正常。

后果：**上面那批 DeepSeek 结果里一直混着思维链**。修复后同一提示词下，
每 run 输出从 **~6100 token 掉到 ~950 token**，成本降到约 1/6
—— 即上一节报的成本（¥0.048 → ¥0.055/次）**高估了约 6 倍**。

这个 bug 只能靠**拦截真实请求体**的测试抓住，测函数返回值是测不出来的
（见 `tests/siliconflow-wiring.test.ts`）。

同一批还修了：
- **`response_format` 不是所有模型都支持**。`GLM-4.5-Air` 直接 400
  `code 20024 Json mode is not supported`，整条运行当场判死、成本记 0，在表里看起来像"模型不行"。
  现在遇此类 400 会去掉该字段降级重试。
- **不传 `max_tokens` = 把上限交给服务端默认值**（硅基是 4096）。`Ling-flash-2.0` 每次都在 4096
  被截断、JSON 永远不完整。现在 `ModelSpec.maxTokens` 统一指定 8192 —— 它同时是一道成本护栏。
- **失败记录被当成"已完成"跳过**，一次网络抖动会被永久固化成"这个模型跑不了"。现在只跳过成功的。
- **`compareRuns` 在两侧没有共同 case 时抛异常**，导致整份报告写不出来（候选在某切片全失败时会触发）。
  现在返回空结果并标注"无法配对比较"。

### "能用"本身就是一次筛选

用真实 prompt 各跑一次完整诊断（不是玩具请求），四个候选当场出局：

| 模型 | 实测结论 |
| --- | --- |
| `inclusionAI/Ling-flash-2.0` | 输出被 4096 截断 ×3；单次真实调用 ~80 秒，288 次要跑一个多小时 |
| `stepfun-ai/Step-3.5-Flash` | 两种关思考写法都无效，默认常开思考 → 成本不可控 |
| `ByteDance-Seed/Seed-OSS-36B-Instruct` | 返回空内容（token 全花在 reasoning 上） |
| `Qwen/Qwen3.5-35B-A3B` | 单步 90 秒超时，一趟 366 秒 |
| `tencent/Hy4-preview` | ✅ 可用、23 秒，但它是腾讯系，与裁判同族 → 不能同时收进矩阵 |

榜单上看不出"输出被截断""默认开思考关不掉""正文为空"这类工程可用性问题 —— 只有真跑才知道。

### 这一批的额外代价：位置偏见偏大

跨族裁判 Hunyuan-A13B 在正反序下打分不一致 **102 条（29.7%）**，
远高于上一批同族裁判的水平。长度偏见正常（秩相关 -0.01）。
28 组样本下，**"建议可执行性"这个维度的结论要打折看** —— 这比拿一个跨族但抖动的裁判
去宣布"谁的可执行性更高"要诚实。

## 五、几个刻意的设计取舍

**1. 不做跨版本轨迹 diff。**
Agent 是非确定的，同一输入跑两次 step 序列可能完全不同，按 step 序号 + 工具名做 LCS 对齐会产出大量碎片和假分叉点。
（LangSmith 也没这么干。）改用 **task 级翻转列表 + 并排人工对照**：只问"这组 case 的通过状态翻了吗"，不问"第几步开始不一样"。

**2. 不做 Elo / pairwise 排名。**
8–12 个用户下 Elo 置信区间宽到没有结论。同样的用户数据改成 **40 条建议人工盲抽检**，用途成立得多。

**3. 检测器必须独立于生成器。**
judge 模型 ≠ 被测模型。否则"自证"会让所有指标失去意义。

**4. 「不显著」是个结论，不是"没结果"。**
报告里每个格子都必须带显著/不显著。24 组样本下，"2.31 → 2.34" 大概率只是 3 条 case 的波动。

**5. 成本差异会淹没一切。**
一个模型整体贵 0.03 元，在 6 个切片上就会复读 6 条"成本显著更差"，把真正的质量退化挤到看不见。
`partitionFindings` 把资源类差异折叠——这是真实跑 demo 时踩出来的，不是设计时就想到的。

## 六、接上真实模型

两条路径并存，共用同一套指标与统计：

```bash
npm run demo         # 离线合成数据，验证管线，永远可跑、不花钱
npm run eval:dry     # 只打印将要发出的 prompt，不发请求 —— 花钱前先确认
npm run eval:smoke   # 冒烟：4 组 case × 1 次
npm run eval         # 全量：24 组 × 矩阵全部档位 × 3 次重复
npm run eval:report  # 只按已落盘数据重新出报告，不花钱、不重跑
```

### 要改什么

**只有 `.env`，一行代码都不用改。**

```bash
cp .env.example .env
# 填一个 key 即可。手上有哪个就用哪个，评测矩阵与裁判会跟着自动切换。
```

| `.env` 里的键 | 作用 | 拿到它的成本 |
| --- | --- | --- |
| `SILICONFLOW_API_KEY` | **推荐**：生成侧跨厂商矩阵 + 裁判（腾讯混元，跨族） | 充值，实测全矩阵 288 次 ≈ **¥2.3** |
| `DEEPSEEK_API_KEY` | 只跑 DeepSeek 矩阵时用 | 充值，实测 **¥0.05/次**（flash，含当时未修 bug 的虚高） |
| `ZHIPU_API_KEY` | 生成侧（GLM-4.5/4.7-Flash） | **免费**，注册即用 |

`src/` 下的指标与统计、`schema.sql`、落库逻辑一行都不用动。

> **矩阵是按"手上有哪个 key"自动切的**：有硅基流动 key → 跨厂商 4 档位矩阵；
> 只有 DeepSeek → DeepSeek 单变量矩阵；都没有 → 智谱免费档兜底。
> 换矩阵不需要改代码，但**换平台会让历史数据不可比**（第三方转发 vs 原厂），
> 同一批结论必须在同一个平台上跑完。

### DeepSeek 的两个坑（实测踩出来的，不是从文档抄的）

**① `deepseek-flash` 默认开思考模式。** 官方文档写明 thinking 默认 `enabled`。
直接调用会返回 `reasoning_content`，正文被 `max_tokens` 截断（`finish_reason: length`），
JSON 解析当场失败；就算不失败，思考 token 也按**输出价**计费，预算直接烧光。
所以 `catalog.ts` 里两个 DeepSeek 模型都带了 `extraBody: { thinking: { type: 'disabled' } }`。

> ⚠️ **光在 catalog 里声明没用**：当时 `offerAgent` / `llmJudge` 构造客户端时漏传了
> `extraBody`，这个参数一直没进请求体 —— 声明了、也写了消费逻辑，中间断链。
> 正确写法见 `src/agent/offerAgent.ts`，回归测试见 `tests/siliconflow-wiring.test.ts`
> （**拦截真实请求体**做断言，测返回值测不出来）。

**② 模型 ID 变了。** 2026 年这一版只有 `deepseek-flash`（V4.1-Flash）和 `deepseek-v4-pro`（V4-Pro）两个。
旧的 `deepseek-chat` / `deepseek-reasoner` 仍能被接受，但都路由到 V4.1-Flash，
且语义是"非思考 / 思考"，不是两个不同的模型 —— 按旧名配矩阵会得出错误结论。
**判断当前可用模型以 `/models` 接口为准**，不要信第三方博客：

```bash
curl -H "Authorization: Bearer $DEEPSEEK_API_KEY" https://api.deepseek.com/models
```

### 评测矩阵的设计意图

三个档位，**每次只改一个变量**，否则分不清提升来自模型还是来自 prompt。

手上只有 DeepSeek key 时（`catalog.ts` 会自动切到这套）：

| 档位 | 模型 | prompt | 回答什么问题 |
| --- | --- | --- | --- |
| `flash__p1-baseline` | DeepSeek-V4.1-Flash | p1-baseline | （基线） |
| `flash__p2-strict` | DeepSeek-V4.1-Flash | p2-strict | **改 prompt** 有用吗 |
| `pro__p1-baseline` | DeepSeek-V4-Pro | p1-baseline | **换模型**有用吗 |

配了智谱 key 时切到 GLM 版本（`glm45/glm47/glm45__p2-strict`），结构完全一样。

两版 prompt 的差别只有一条：p2-strict 强制每条建议绑定段 ID，并禁止引入简历里没有的数字与实体。

**V4-Pro 这一档默认不跑**：实测它单次产出 ¥0.377，是 flash（¥0.051）的 7.4 倍，24 组 × 3 次的完整对照要 ¥27，
和"学生项目 ¥100 预算"的设定对不上。要跑就用 `--profile pro__p1-baseline` 单独加。
**代价要写在结论里**：不跑这一档，就没有资格说"换更贵的模型有没有用"。

### 成本

**¥0。** GLM-4.5-Flash / 4.7-Flash / 4-Flash 永久免费、不限 token；硅基流动的 Qwen3-8B 也免费。
全量跑（约 800 次调用）的真实账单是 0 元。`--budget` 默认仍设 ¥100 硬上限，
万一你换成付费模型，超线会立刻停止派发新任务（已在飞的请求跑完，已完成结果保留）。

### 断点续跑

中断了直接重跑即可，已完成的 `(run_id, case_id, run_index)` 会被跳过。

**这里踩过一个 bug，值得记一笔。** 早先的实现按"trace 文件是否存在"判断是否已完成，
但跳过时**不写回 runs JSONL** —— 结果是一次中断之后重跑，汇总只读到本次新写的记录，
被跳过的那批凭空消失（6 组任务跑完，汇总里只剩 1 组）。
现在改成：**runs JSONL 是唯一事实来源**，断点判断和汇总都读它，并且汇总会把
`data/real/` 下所有 `runs-*.jsonl` 取并集。

### 成本口径：缓存命中必须单独计价

DeepSeek 有自动上下文缓存，命中部分的输入单价约为未命中的 **1/50**
（flash 峰时 $0.006 vs $0.30）。本项目的 system prompt 与简历正文在不同 case 间高度重复，
命中率不低 —— 一律按未命中价计费，成本报告会虚高一个量级。
所以 `costOf(model, in, out, cachedIn)` 第四参数是必须传的，`usage.prompt_cache_hit_tokens` 直接喂进去。

另外**价格表用的是峰时价**（峰时 = 谷时 2 倍），也就是说报告里的成本是**刻意高估**的。
宁可把预算估高提前停，也不能估低跑超。谷时（含周末全天）实际只花一半。

### 接真实模型后新增的几道防线

**① 锚点必须真实存在。** 模型很擅长编一个 `S09` 出来冒充"有出处"。
`offerAgent` 会把不存在的段 ID 一律置 null（不让假锚点灌水覆盖率），
同时记进 `invalidAnchors` 单独暴露——"假装有出处"本身是个值得看的信号。

**② judge 要尽量换族。** 选择顺序：有硅基流动 key → Qwen3-8B（最干净）；
智谱 + DeepSeek 都有 → 用 V4-Pro 裁 GLM 的输出；**只有 DeepSeek → 只能用 V4-Pro，同族**，
运行时会明确打警告。同族裁判有系统性偏袒，"可执行性"的结论就不可信 —— 这不是洁癖，是结论有效性。

**③ 位置偏见要量化。** 同一条建议正反序各打一次分，报"两次不一致的条数"。
如果这个比例很高，说明打分对顺序敏感，结论不能直接用。

**④ 长度偏见要检查。** 建议长度与得分的秩相关 > 0.5 就打警告——
那意味着 judge 基本在按长度打分，不是按可执行性。

**⑤ judge 的说服力靠人工校准。** 把人工标注放到 `data/gold/labels.jsonl`，
运行时会自动算 judge 与人的一致率、κ、Spearman 和系统性偏差。
**这个文件不存在时，报告会明确写"未经人工标注校准，judge 打分只能当参考"。**

### 无源实体率：为什么报两个口径

这是**第一批真实数据教出来的**，不是设计时想到的。第一次跑完，无源实体率算出来 0.43，
看着像"模型在大面积编造"。逐条读输出才发现，命中的实体大多长这样：

> 建议把这一句拆开，**例如：「每 15s 发送心跳 ping，连续 2 次无 pong 判定掉线」**

`15s`、`2 次`都不在简历里，规则判它"无源"，技术上没错 —— 但它是给候选人的**填写模板**，
不是"我断定你有这个经历"的断言。把两者塞进同一个分子，指标就废了。

所以现在 `unsourcedRate()` 同时返回两个数：

| 口径 | 含义 | 用途 |
| --- | --- | --- |
| `rate` | 严口径，示例里的实体也算无源 | 保守，适合对外宣称 |
| `rateExcludingExamples` | 只统计对简历的断言 | 反映"有没有编造事实" |

两个数都印在报告里，因为**哪个更对取决于想问什么**，不该由代码单方面决定。
识别示例片段的逻辑在 `exampleSpans()`：成对的 `「」`/`『』`，且引号前面 15 字内出现
"例如/改成/示例"这类提示词，或片段内出现 `__`、`XX` 之类占位符。

### 三种裁判/生成配置的取舍

| 场景 | 生成侧 | 裁判侧 | 成本 | 跨族 |
| --- | --- | --- | --- | --- |
| 最推荐 | 智谱 GLM-4.5/4.7-Flash | 硅基流动 Qwen3-8B | **¥0** | ✅ |
| 只有 DeepSeek（本次实际用的） | deepseek-flash | deepseek-v4-pro | 实测约 ¥0.05/次 | ⚠️ 同族 |
| 智谱 + DeepSeek | 智谱 GLM-Flash | deepseek-v4-pro | 生成 ¥0，裁判按量 | ✅ |
| 完全离线 | Ollama `qwen2.5:7b` | Ollama 另一个模型 | ¥0 | ⚠️ 慢、质量差 |

**结论：如果想要一个"干净"的裁判，去 https://cloud.siliconflow.cn/ 注册一个免费 key 就够了**
（需实名）。加一行 `SILICONFLOW_API_KEY=`，裁判自动切成跨族的 Qwen，其余不用动。

### 关于"能不能用 WorkBuddy 积分"

不能。WorkBuddy 的积分是助手自身对话的额度，不是一条通用的文本模型 API 网关，
没法在你的脚本里拿它去发 LLM 请求。好在真花钱的口子被压得很小：
本次全量真实评测（144 次 Agent 运行 + 96 次裁判调用）**实际花费约 ¥4–5**。
